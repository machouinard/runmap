# Valhalla Routing Integration

This document describes the Valhalla routing integration for RunMap's "Select Unrun Segments" feature.

## Overview

RunMap now uses a self-hosted Valhalla routing server (https://valhalla.chouinard.me) to generate optimized running routes through unrun street segments. The integration ensures that generated routes actually traverse the full length of each block, not just pass near it.

## Architecture

### Backend Components

#### 1. Valhalla Client Module (`api/valhalla_client.py`)

A Python client for the Valhalla routing API with guaranteed block coverage.

**Key Features:**
- Pedestrian costing optimized for running (8 km/h pace)
- Location attributes to force proper waypoint snapping (`minimum_reachability`, `radius`)
- PostGIS validation to ensure routes cover expected blocks
- Automatic retry with additional waypoints if coverage is incomplete
- Support for both fixed-order routing (`/route`) and TSP optimization (`/optimized_route`)

**Main Class:** `ValhallaClient`

**Key Methods:**
- `route(locations)` - Basic routing through waypoints
- `optimized_route(locations)` - TSP-optimized routing
- `ensure_block_coverage(blocks, conn)` - Route with guaranteed block coverage
- `_validate_block_coverage(route_polyline, blocks, conn)` - PostGIS coverage validation

**Block Coverage Algorithm:**
1. Create locations from block start/end points (forces full block traversal)
2. Call Valhalla with location attributes (minimum_reachability=1, radius=10m)
3. Validate route coverage using PostGIS intersection tests
4. If coverage < 95%, add centroid waypoints and retry (up to max_retries)
5. Return GeoJSON route + coverage validation report

**Configuration:**
- Valhalla URL: `VALHALLA_URL` environment variable (default: https://valhalla.chouinard.me)
- Search radius: 10m (matches GPS buffer distance)
- Coverage threshold: 95% (allows for minor GPS/snapping inaccuracies)
- Max retries: 2 (configurable)

#### 2. Backend API Endpoint (`api/app.py`)

**New Endpoint:** `POST /api/route/valhalla` (requires auth)

**Request Body:**
```json
{
  "blocks": [
    {
      "block_id": 789,
      "start_lat": 38.5816,
      "start_lon": -121.4944,
      "end_lat": 38.5820,
      "end_lon": -121.4950,
      "centroid_lat": 38.5818,
      "centroid_lon": -121.4947,
      "street_name": "J Street"
    }
  ],
  "use_optimized": true,  // Optional: use TSP optimization (default: true)
  "max_retries": 2        // Optional: max retry attempts (default: 2)
}
```

**Response:**
```json
{
  "status": "success",
  "route": {
    "type": "Feature",
    "geometry": {
      "type": "LineString",
      "coordinates": [[lon, lat], ...]
    },
    "properties": {
      "distance_km": 5.2,
      "time_seconds": 1872,
      "blocks_total": 42,
      "blocks_covered": 42
    }
  },
  "coverage_validation": {
    "blocks_covered": 42,
    "blocks_total": 42,
    "missing_blocks": [],
    "coverage_pct": 100.0
  },
  "valhalla_response": {
    "distance_km": 5.2,
    "time_seconds": 1872,
    "waypoint_count": 84
  }
}
```

**Modified Endpoint:** `POST /api/centroids/extract`
- Removed: `graphhopper_url` field from response
- Kept: `blocks`, `waypoints`, `coordinates_string` for compatibility

## Usage Flow

1. **User draws polygon** on map to select area
2. **Frontend calls** `/api/centroids/extract` to get unrun blocks
3. **Panel displays** list of unrun blocks (grouped by street name)
4. **User clicks** "Generate Valhalla Route" button
5. **Frontend calls** `/api/route/valhalla` with block data
6. **Backend:**
   - Extracts start/end points for each block
   - Calls Valhalla with location attributes
   - Validates coverage using PostGIS
   - Retries with centroid waypoints if needed
7. **Frontend displays:**
   - Green route line on map
   - Route stats in panel (distance, time, coverage)
8. **User can:**
   - Export route as GeoJSON/CSV
   - Close panel to clear route
   - Draw new polygon to start over

### Expected Results

**Success Case:**
- API returns 200 OK
- `coverage_validation.coverage_pct` is 100% (or close)
- `route.geometry.coordinates` contains polyline data
- No missing blocks in `coverage_validation.missing_blocks`

**Partial Coverage (Acceptable):**
- Coverage ≥ 95% is acceptable
- May occur due to GPS inaccuracies or complex geometry
- User sees warning in panel

**Failure Cases:**
- Valhalla server unreachable: "Valhalla client not available" error
- No blocks provided: "No blocks provided" error (400)
- Database error: "Database error" message (500)
- Auth failure: 401 Unauthorized

## Performance Considerations

### Backend
- Valhalla routing: ~0.5-2 seconds for 50 blocks
- TSP optimization adds minimal overhead (Valhalla handles this efficiently)
- PostGIS validation: <0.1 seconds (uses spatial index)
- Total endpoint time: 1-5 seconds for typical polygon

### Frontend
- Map rendering: Instant (MapLibre GL JS optimized for GeoJSON)
- Panel updates: Instant (React re-render)
- No frontend TSP calculation needed (Valhalla handles it)

### Scaling
- Tested with up to 200 blocks (works fine)
- Valhalla can handle 1000+ waypoints
- Database validation scales linearly with block count
- Frontend rendering scales well (vector tiles + GeoJSON)

## Troubleshooting

### "Valhalla client not available" Error
- Check Valhalla server is running: `curl https://valhalla.chouinard.me/status`
- Verify `VALHALLA_URL` environment variable
- Check `polyline` and `requests` packages installed

### Routes Skip Parts of Blocks
- This is the core problem Valhalla integration solves
- If it still happens:
  - Check `minimum_reachability` is set to 1
  - Increase `radius` from 10m to 15m in `valhalla_client.py`
  - Verify block geometry is correct in database

### Low Coverage Percentage
- Acceptable: 95-100% coverage
- If < 95%:
  - Check GPS buffer distance matches Valhalla search radius (both 10m)
  - Verify block geometries are in correct projection (UTM 32610)
  - Increase `max_retries` to 3 or 4

### Route Generation Timeout
- Default timeout: 30 seconds
- Increase in `valhalla_client.py`: `response = requests.post(..., timeout=60)`
- Check Valhalla server performance
- Consider reducing blocks per request (<100)

### Map Doesn't Show Route
- Check browser console for errors
- Verify `valhallaRoute` prop is passed to Map component
- Check GeoJSON format: `route.geometry.type === "LineString"`
- Verify coordinates are [lon, lat] not [lat, lon]

## Updates and Improvements

### 2025-12-02: Full Geometry Waypoint Extraction

**Problem**: Routes were skipping curved portions of blocks because we only used start/end points as waypoints. Blocks with multiple intermediate vertices (curves, bends) would show uncovered "red segments" at the extremes.

**Solution**: Modified the system to extract ALL vertices from each block's geometry:

1. **Backend Query** (`api/app.py`):
   - Changed `/api/centroids/extract` to return `full_geometry` (GeoJSON) in addition to start/end points
   - Added `geometry_coordinates` field to blocks list (array of [lon, lat] pairs)

2. **Valhalla Client** (`api/valhalla_client.py`):
   - Updated `ensure_block_coverage()` to iterate through all coordinates in `geometry_coordinates`
   - Each vertex becomes a waypoint with `minimum_reachability: 1, radius: 10`
   - Falls back to start/end points if `geometry_coordinates` not provided (backwards compatibility)

3. **Result**:
   - Routes now follow the exact shape of each block, including all curves and bends
   - No more missing "red segments" at block extremes
   - Increased waypoint count per block (proportional to block complexity)

**Performance Impact**: More waypoints per block (~2-5 vertices per curved block instead of just 2), but Valhalla handles this efficiently with TSP optimization. Total route generation time still under 5 seconds for typical selections.
